## 07 · ② 研究過程 · 實際做法 01 ｜ 40s

```
Figma ⇄ Storybook 同步
Design System 迴圈：元件怎麼從設計稿，變成 vibe coding 裝得到的套件

┌─────────┐    ┌───────────┐    ┌────────┐    ┌───────────┐
│Figma 元件│───▶│Design Ready│───▶│Draft PR│───▶│Storybook 元件│
│設計師的   │設計師│版本        │Webhook│只有任務檔│工程師用  │發布成套件，  │
│工作環境   │調完 │手動建立，   │驗證後 │不含 code│Figma MCP│vibe coding │
└────▲────┘宣告 │格式要對     │自動開 └────────┘同步，再比對│裝得到       │
     │     完成 └───────────┘  ▲橘      差異、補上└───────┬───┘
     │                          橘框      元件功能         │
     └──────── 發布後 Figma 和 code 回到對齊 ───────────────┘
```

**講法**：字寫在線上——節點是「東西」，線上是「怎麼過去的」。中間橘框那格是唯一自動的一段，而且它**只開 PR，不動 code**。

> 版上放不下但值得講：Figma MCP 帶過來的是**樣式跟結構**，元件的**功能**要工程師自己補。

## 08 · ② 研究過程 · 實際做法 02 ｜ 35s ⭐

```
使用 Storybook 套件進行 vibe code
透過 skill 達成：Storybook 元件 ＋ 設計師的 UX 心法

01 ds-craft          02 ds-studio        03 ds-sense  ← 橘框
嚴格管制：違規就擋下    再加上策略與驗證關卡   當參考材料，不當合規清單
28 KB 規範 · 9 步流程  20 KB 規範 · 8 階段  3 KB 規範 · 4 步
3 個 Subagent        6 個 Subagent       0 個 Subagent
✗ 不準，而且很燒 token ✗ 更完整，也更燒     ✓ 準一點，也便宜很多

Step ▸ 管得越嚴，AI 反而做得越差
```

**講法**：這次研究最誠實的一頁。三個 skill 裝的東西一樣，差別在「管多嚴」。我以為管得不夠完整 → 加更多關卡 → 更貴但沒更準 → 反過來砍掉 → 才變好。

規模差異本身就是論證，數字念出來就好。收尾補一句解釋：**規範太細的時候，它花力氣在滿足檢查，不是在把畫面做對。**

## 09 · ② 研究過程 · 產出 ｜ 1:45

**兩段 build。** 圖照 `docs` 外部的協作 flow（FigJam）簡化。

**build 1 — 三泳道主路徑 + 兩條退回**

```
PM      PRD ─vibe code─▶ POC ─────────────────────▶ 整體需求確認 ─通過─┐
                          │                          ▲    │不通過      │
設計師                UI/UX 討論 ─▶ 檢視 UX ─不通過─▶ 提出修改  │         │
                          ▲          │通過            │      ▼         │
                          │          ▼                │ Figma 細節與   │
工程師                  修改前端 ◀────┘          檢視 UI/UX  元件調整     │
                                  前端轉入 Figma ─▶  ▲   │不通過 │       │
                                                    └ 修改前端 ◀┘     開發
```

**build 2 — Design System 迴圈 + 兩條虛線**

```
        skill 套用 ╌╌╌╌╌╌╌╌╌╌            import ╌╌╌╌╌
┌──────────────────────────────────────────────────────┐
│ Design System 迴圈 · 設計師 → 工程師                    │
│ 調整／新增共用元件 → Figma Design System → Storybook → DS 套件 │
└──────────────────────────────────────────────────────┘
```

**這頁只要傳達三件事**（不要逐節點講）：

1. **三道檢視**：檢視 UX（設計師）→ 檢視 UI/UX（設計師）→ 整體需求確認（PM）
2. **修正一律改前端**。三條退回路徑最後都導向「修改前端」——`vibe code` 只在最開頭跑一次，後面都在同一份前端上改。差別在改之前設計師先做什麼：第一關只「提出修改」（**不碰 Figma**），第二三關才進「Figma 細節與元件調整」。**Figma 出現的時機是被設計過的。**
3. **兩條虛線把上下接起來**：PM 做 POC 時透過 skill 吃套件，工程師改前端時 import 套件——**兩邊拿的是同一包**。

> 💡 圖上沒有「畫設計稿」這個動作。這句用口說指出來，讓觀眾自己去圖上找。
> 💡 前面超時的話這頁最先被壓：只講 build 1 +「下面是元件庫怎麼維護的，細節等等聊」。

## 10 · ③ 遇到的問題 ｜ 1:45

```
遇到的問題

01 設計不準            02 SSOT 問題              03 同步失真問題
─────                 ─────                     ─────
POC · 修改前端          Figma 細節與元件調整         前端轉入 Figma
元件拿對了，版面還是會跑   Figma 與 Storybook         vibe code 轉進 Figma，失真一次
                       各有一份 Design System     Figma 調完再轉回真實前端，又失真一次
```

灰色小字是**這個問題發生在第 9 頁流程圖的哪一格**——上一頁剛看完，這裡點名位置，問題就從抽象抱怨變成可以指認的東西。

**講法要點**

- **01**：不準不是被 skill 擋掉的，是被三道人工檢視一次次撈出來的。而且不是規範寫得不夠——我砍規範反而變準（回收第 8 頁）。
- **02**：元件層方向明確（Figma DS → Storybook），但兩邊都存在一份 DS，誰是準的沒有定論。
- **03**：失真是**累積的**，不是一次性的。兩個檢視關卡不通過都會回到「Figma 細節調整 → 修改前端」，每輪來回再掉一次。

> 根因（口說，版上不寫）：**「元件」這一層我們做成了系統，「怎麼組成畫面」還停在人工。** 三個問題同一個根——組法沒被定義、沒被記錄、沒有可對應的表示法。

## 11 · ④ 心得 ｜ 1:30 ⭐

```
心得

一 · AI 做設計還是有差距
它做得出「像設計的東西」，              ← 40px 灰
做不出「對的設計」。                    ← 48px 粗 + 螢光筆
─────────────────────────────
二 · vibe code 的風險藏在優點裡
它很快，能直接生出會動的 POC，           ← 40px 灰
風險不是做得爛，是做得「看起來很好」。      ← 48px 粗 + 螢光筆
```

**兩點結構對仗**——同一個病，一個講 AI 的產出、一個講 vibe code 的產物：

| | 表面 | 實際 |
|---|---|---|
| 一 | 像設計的東西 | 不是對的設計 |
| 二 | 看起來很好 | 不是真的好 |

**講法**

- 一：用 28 KB → 3 KB 那個實測堵掉「那你多寫一點規範不就好了」。收在**「它缺的不是規則，是判斷。」**
- 二：優點就是風險的來源，不是「有好有壞」。完成度看起來高，人就容易跳過該有的檢查。
- 收尾可留一句：「不是不信任 AI，是因為它太會裝了。」留著全場會笑，也會記住。
